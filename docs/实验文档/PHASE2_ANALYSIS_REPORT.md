## 📊 核心发现与分析

### 调度方法优化方向分析

#### 方向1：Phase-Aware DVFS（阶段感知频率调节）✅ 强烈推荐**

**设计原理**：
Prefill 阶段（主要是大矩阵计算）和 Decode 阶段（主要是 KV cache 访问和小矩阵乘法）使用不同的频率配置。

**关键发现**：
- Prefill 阶段：GPU 计算密集，高 GPU 频率显著提升吞吐，对 EMC 频率不敏感
- Decode 阶段：KV cache 访问密集，高 EMC 频率显著减少 token latency，对 GPU 频率相对不敏感
- CPU 频率：主要影响控制路径延迟（TTFT），对吞吐量影响较小

**频率配置策略**：
```
Prefill:   GPU=high, CPU=high, EMC=mid
Decode:   GPU=mid,  CPU=mid, EMC=high
```

**预期收益**：
- 能效提升：15-20%（相比固定配置）
- 性能保持：Prefill 阶段维持高吞吐，Decode 阶段维持低延迟
- 切换开销：可在阶段边界切换，开销可接受（<50ms）

**实施复杂度**：中等
- 需要准确的阶段识别机制

#### 方向2：Workload-Aware 自适应调度⭐ 强烈推荐

**设计原理**：
根据工作负载特征（batch size, prompt length, output length, 并发度）从能耗汇率表中查找或预测最优配置。

**关键特征**：
- Batch size: 影响计算资源利用率
- Prompt length: 影响 prefill 阶段的时间和能耗
- Output length: 影响 decode 阶段的总时间和能耗
- Phase: 当前推理阶段（prefill/decode/mixed）
- Concurrency: 影响资源竞争和调度效率

**配置选择策略**：
1. 提取当前请求的特征
2. 查询能耗汇率表查找匹配配置
3. 如果有精确匹配，直接使用
4. 如果没有匹配，使用最近邻或插值
5. 验证 SLO 满足度
6. 如果不满足 SLO，调整到满足 SLO 的配置

**预期收益**：
- 自适应性：自动适应不同的负载模式
- 能效优化：针对不同负载使用最优配置
- 快速响应：查表方式响应迅速（<10ms）
- SLO 保证：始终满足服务级别目标

**实施复杂度**：中等
- 需要完整的能耗汇率表作为基础

#### 方向3：多目标 Pareto 优化

**设计原理**：
在能耗、延迟、吞吐量等多个目标之间寻找 Pareto 最优配置集合。

**关键要点**：
- 主目标：最小化 energy/token
- 约束条件：TTFT < 1000ms, TPOT < 80ms, 功耗 < 40W, 温度 < 80°C
- 权衡机制：在满足 SLO 的前提下最小化能耗
- 可视化：提供清晰的 Pareto 前沿图

**预期收益**：
- 全局最优：在给定约束下找到最有效的配置
- 权衡透明：清晰展示不同配置的权衡关系
- 灵活性：可根据应用场景调整优化目标权重

**实施复杂度**：中等
- 需要优化算法（如 NSGA-II, Multi-objective evolutionary algorithms）

#### 方向4：混合智能调度

**设计原理**：
结合基于规则的方法（Phase-aware DVFS, Workload-aware）和机器学习方法（强化学习）的优势。

**规则层**：
- 提供基础的可预测性和安全性
- 处理常见场景的快速响应
- 确保 SLO 满足和系统稳定性

**学习层**：
- 通过在线学习持续优化调度策略
- 适应新的负载模式和系统状态变化
- 发现人类难以发现的优化机会

**预期收益**：
- 鲁棒性：规则方法保证基本功能，学习方法持续改进
- 自适应性：可以自动适应环境变化
- 长期优化：通过学习不断接近最优调度

**实施复杂度**：高
- 需要完整的机器学习基础设施
- 需要充分的训练数据和验证

### 关键技术要点

#### 1. 频率切换策略
**Hysteresis 机制**：
- 最小保持时间：GPU/CPU 5秒，EMC 2秒
- 切换阈值：GPU/CPU 变化 > 100MHz，EMC > 400MHz
- 目的：避免抖动和频繁切换

**边界切换**：
- 优先在 prefill/decode 阶段边界切换
- 避免在 token 级别进行切换
- 可以在 request boundary 或 batch window boundary 切换

**预测性切换**：
- 根据预测的负载模式提前调整配置
- 在负载变化之前完成切换，减少影响

#### 2. SLO 约束处理机制
**硬约束（必须满足）**：
- TTFT < 1000ms（P95）
- TPOT < 80ms（P95）
- 功耗 < 40W（平均值）
- 温度 < 80°C（P99）

**软约束（优先保证）**：
- P99 latency < 150ms
- Throughput > 20 tokens/s
- Energy/token 最小化

**约束验证**：
- 实时监控当前指标
- 提前预测和调整
- 违反检测和告警
- 安全回退到已知安全配置

#### 3. 数据驱动决策
**统计验证**：
- 确保配置选择基于充分的实验数据
- 使用置信区间评估不确定性
- 通过 A/B 测试验证改进

**特征重要性分析**：
- 分析哪些 workload 特征对性能影响最大
- 指导配置优化方向

**模型选择**：
- 从简单模型（线性回归）开始
- 根据验证结果决定是否需要复杂模型

#### 4. 系统集成考虑
**与 TensorRT-LLM 集成**：
- 通过环境变量或配置文件传递频率设置
- 监控 TensorRT-LLM 的性能指标

**与监控系统集成**：
- 从 tegrastats 获取功耗和温度数据
- 统一的性能监控平台

**与用户接口集成**：
- 提供 REST API 或配置接口
- 支持动态 SLO 调整
- 性能指标暴露和告警

## 🚀 实验设计更新总结

### 用户要求的关键更新

#### 1. 使用所有频率档位进行对比
**原有设计**：仅使用 low/mid/high 三档频率
**更新设计**：使用 Jetson Orin 的所有可用频率档位进行对比

**更新的频率配置**：
- GPU 频率：13 档（从 378MHz 到 1428MHz 的所有可用档位）
- CPU 频率：10 档（从 1020MHz 到 2015MHz 的所有可用档位）
- EMC 频率：7 档（从 133MHz 到 2133MHz 的所有可用档位）

**影响**：
- 实验规模大幅增加（从 27 个组合增加到数百个）
- 需要更长的实验时间
- 需要更好的采样策略（避免全组合爆炸）

#### 2. 能效对比逻辑更新
**原有逻辑**：对比所有配置的能效表现
**更新逻辑**：只在满足 SLO 的条件下进行能效对比，不满足 SLO 的点应该在对比中被去除

**影响**：
- 更加公平和准确的能效评估
- 避免不满足 SLO 的配置被错误地认为"高效"
- 确保 SLO 是优化的硬约束，不是软目标

#### 3. 优化的 baseline 策略
**新增 baseline**：除了传统的 MaxN 和 Default Governor 外，新增：
- **Balanced-Efficiency**: 中档 GPU + 中档 CPU + 高档 EMC（平衡的能效配置）
- **Low-Power**: 低档 GPU + 低档 CPU + 中档 EMC（低功耗配置）
- **Scenario-Optimal**: 根据具体场景优化的配置

**目的**：
- 提供更多有意义的对比基准
- 展示不同优化策略的效果
- 支持不同应用场景的选择

## 📊 实验执行策略

### 实验优先级
1. **高优先级**：验证测量稳定性（实验 4.1）
   - 这是所有实验的基础
   - 不需要完整的频率配置
   - 可以快速验证系统可行性

2. **中优先级**：单旋钮敏感性实验（实验 4.2）
   - 快速了解不同频率旋钮的影响
   - 使用部分频率档位进行测试（避免全组合爆炸）
   - 生成热力图，提供快速可视化

3. **中优先级**：Prefill/Decode 阶段差异实验（实验 4.4）
   - 验证分阶段 DVFS 的核心假设
   - 使用代表性配置进行测试
   - 4 个场景 × 3-5 个配置 = 20-40 次运行

### 采样策略
1. **分层采样**：避免全组合爆炸
   - 先粗粒度扫描找到大致范围
   - 再在感兴趣区域进行细粒度采样
   - 逐步聚焦到最有潜力的配置

2. **代表性采样**：选择有代表性的配置组合
   - 覆盖不同频率水平的组合
   - 平衡探索效率和实验成本

3. **增量式实验**：先做小规模验证
   - 根据结果调整后续实验设计
   - 避免一次性进行大规模实验发现后期无法调整
