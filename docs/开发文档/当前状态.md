### 方向调整说明

Phase 7 实验证明：基于 sysfs/debugfs 的 phase-boundary hard DVFS 切换开销约 715ms，
占 TTFT 的 37-65%，无法在单次请求内获得稳定收益。因此项目转向：

**离线 lock-frequency profiling + 在线 workload/thermal-aware frequency cap**

核心思想：离线用 lock mode 精确测量能耗边界，在线用 cap mode 设置频率上限，
让 Jetson governor 在 cap 范围内快速动态调节。

### Phase 8-9 完成内容

**Phase 8: CapController (src/controller/cap_controller.py)**
- `lock_config()`: 强制精确频率，用于离线 profiling
- `set_cap()`: 设置频率上限，保留动态 governor，用于在线控制
- `restore_dynamic()`: 恢复默认 governor 和完整频率范围
- `read_actual_state()`: 读取当前频率、governor、温度
- cap mode 不强制 min=max，apply latency 显著小于 lock mode

**Phase 9: benchmark_mode (src/benchmark/llama_cpp_runner.py)**
- `run_single_inference(benchmark_mode=True)`: temperature=0, repeat_penalty=1.0
- 使用 logit_bias 抑制 EOS token，确保模型输出到 max_tokens
- 实测：o=512 时 normal mode 仅输出 208 tokens，benchmark_mode 输出 512/512
- 新增字段：is_complete_output, completion_ratio, benchmark_mode

### P8: 细粒度 GPU×EMC 能耗 Profiling (已完成 2026-05-16)

**动机**: Phase 5/7 的实验仅使用 4 GPU × 2 CPU 配置，缺少 EMC 频率维度。
通过 DebugFS 实现 EMC 频率控制，扩展至完整硬件配置空间。

**实验矩阵**: 11 GPU × 4 EMC × 1 CPU = 44 配置
- GPU: 306-1300 MHz (11 档)
- EMC: 204-3199 MHz (4 档，通过 `/sys/kernel/debug/emc/` 控制)
- CPU: 1036 MHz (固定)

**Decode phase**: 660 runs (5 workloads × 3 repeats × 44 configs)
**Mixed phase**: 660 runs (同上)
**合计**: 1320 runs

**关键发现**:
- GPU 频率效率曲线呈 W 形：GPU612 和 GPU816 是能效最优点
- EMC 204 MHz 反而最节能（小模型 Phi-3-mini 3.8B 内存带宽不是瓶颈）
- 最优能效配置：**GPU816 + EMC204** (E/tok ≈ 0.97J, TPOT ≈ 33ms)

## Phase 7 进行中：真正 Phase Switching 验证

### 背景与动机

Phase 6 的 E2E benchmark 显示不同配置的 E/token 差异 <3%。经分析，主要原因：
1. Phase-aware 策略实际上没有真正在线切频 — 只是用 decode config 跑完整推理
2. Prefill 占比大，稀释了 decode 阶段的 DVFS 差异
3. 所有 baseline 都接近 Pareto 最优，差距自然小
4. 静态功耗占比高，DVFS 可调空间有限
5. 模型较小（Phi-3-mini 3.8B），DVFS 优化空间有限

### 实验设计

**核心改进**：在 `llama_cpp_runner.py` 中新增 `run_phase_split_inference()` 方法，支持在 prefill→decode 边界实时切换频率配置。

**实验矩阵** (234 runs, ~3.2 hours):
- Part 1: 真正 Phase-Switching (3 alpha × 8 workloads × 3 repeats = 72 runs)
- Part 2: 单一配置对照 (3 alpha × 8 workloads × 3 repeats = 72 runs)
- Part 3: 强 Baseline (MAXN/30W/E_min × 8 workloads × 3 repeats = 72 runs)
- Part 4: 弱 Baseline (动态调频/最低频/随机配置 × 2 workloads × 3 repeats = 18 runs)

**新增 workload（更长 decode）**:
- p128_o512 (128 prompt, 512 output)
- p128_o1024 (128 prompt, 1024 output)
- p512_o1024 (512 prompt, 1024 output)

**弱 Baseline**:
- `dynamic_governor`: GPU simple_ondemand + CPU scheduit 动态调频
- `min_freq`: 全最低频 (GPU306 + EMC204 + CPU1036)
- `random_config`: 随机频率组合

### 新增文件

- `src/benchmark/llama_cpp_runner.py` — 新增 `run_phase_split_inference()` 回调方法
- `src/experiments/run_phase_switch_e2e.py` — 真正 phase-switching E2E benchmark
- `src/visualization/visualize_phase_switch_e2e.py` — Phase-switch 结果可视化

## 技术风险和限制

1. **GPU Governor 兼容性**: `userspace` governor 在推理负载下不可靠，必须使用 `performance` governor。`schedutil` 不适用于 GPU devfreq。
2. **EMC 频率控制**: 通过 DebugFS 控制，需要 root 权限。部分 GPU×EMC 组合实际上无法生效（硬件限制）。
3. **模型单一性**: 仅验证 Phi-3-mini，需扩展到其他模型
4. **热效应**: 长时间运行的 thermal throttling 未建模
5. **E2E 差异**: Phase 6 E2E 差异 <3%，Phase 7 通过真正 phase switching + 长 decode + 弱 baseline 验证
6. **提前 EOS**: 部分 workload 模型提前结束输出，影响 E/token 对比。已增加 `is_complete_output` 字段
