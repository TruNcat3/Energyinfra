### 方向调整说明

Phase 7 实验证明：基于 sysfs/debugfs 的 phase-boundary hard DVFS 切换开销约 715ms，
占 TTFT 的 37-65%，无法在单次请求内获得稳定收益。因此项目转向：

**离线 lock-frequency profiling + 在线 workload/thermal-aware frequency cap**

核心思想：离线用 lock mode 精确测量能耗边界，在线用 cap mode 设置频率上限，
让 Jetson governor 在 cap 范围内快速动态调节。

### P2: Thermal-SLO Feedback Controller ✅ 合成验证通过

**文件**: `src/controller/thermal_slo_controller.py` (693 行)

窗口级（10s）反馈控制器，6 级优先级规则：

| 优先级 | 规则 | 动作 |
|:---:|------|------|
| 1 | SLO violation > 10% | 立即升频 |
| 2 | 温度 > 85°C (critical) | 升至 max（快速完成→空闲冷却） |
| 3 | 温度 > 75°C + SLO 裕度 + 连续 K window | 降频一步 |
| 4 | 功率超限 + SLO 裕度 + 连续 K window | 降频一步 |
| 5 | 距上次切频 < 20s | 跳过 |
| 6 | 默认 | 保持 |

**关键设计**: Thermal protection 升频不降频（高温需快速完成请求后空闲冷却）。

**合成验证**: 36-window 升温 trace，W27-29 连续满足 hysteresis→降频，W30 SLO violation→回弹。逻辑正确。

## 问题分析与可解决性

### 已解决的问题

1. **单请求 E/tok 天花板** — Oracle Gap +4.9%，确认离线→在线 pipeline 已接近最优
2. **控制器设计** — 6 级优先级 + hysteresis + cooldown，合成 trace 验证通过
3. **实验框架** — 5 baseline × 3 trace serving benchmark 代码完成

### 待验证的假设

1. **热效应可利用** — 主动降频→避免 throttling→整体吞吐更高？（需 P3 数据）
2. **Pareto 功率优势在长期运行中保持** — 7B -18.6% 功率能否转化为温度降低？（需 P3 数据）
3. **10 档 cap 比 4 档更精细** — Pareto 前沿大小对比（需 P1 数据）

### 技术风险

1. **EMC 频率控制失效**: DebugFS min/max_rate 可写入但 clk_rate 不受约束
2. **GPU Governor**: simple_ondemand 不尊重 max_freq，cap mode 必须用 performance governor
3. **8B 优化空间极小**: memory-bound 导致 408MHz 以上 TPS 扁平
4. **ThermalSLO 升频策略可能适得其反**: thermal throttling 已触发时升频可能加剧发热
